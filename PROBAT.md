# PROBAT.md — the self-notarising audit chain

> *DONNA probat.* — DONNA proves it.
>
> This file is the audit chain of this repository, generated by DONNA's own substrate. Every commit on `main` extends the chain. Each record below is an **IDR (Intent Decision Record)** — `decision_id`, `previous_hash`, signed with HMAC-SHA256, replayable, verifiable. See [`bin/notarise`](bin/notarise) (Python stdlib, no dependencies).
>
> *The repository notarises itself. Verify any entry locally.*

---

## How to verify

```bash
# Set a verification key (any 32-byte hex secret works for read-only verification
# IF you have the chain's signing key; the public chain below was signed with the
# project's published demo key — see Appendix B at the bottom of this file).
export DONNA_NOTARISE_KEY=donna-public-demo-key-2026-05-08

# Verify the whole chain
bin/notarise verify --chain PROBAT.md

# Verify a single entry (1-indexed)
bin/notarise verify --chain PROBAT.md --at 2

# Generate a 3-entry sample chain and pipe it back through verify (sanity check)
bin/notarise demo > /tmp/sample-chain.md && bin/notarise verify --chain /tmp/sample-chain.md
```

If `bin/notarise verify` exits 0, the chain is intact. If it exits 1, the chain has been tampered with — and the failure message tells you which entry broke and how.

## The chain (genesis → main HEAD)

The first three entries are the project's bootstrap. They are signed with the published demo key and verify locally with `bin/notarise verify --chain PROBAT.md`. From entry 4 onward the chain grows automatically: the `probat-extend` CI workflow appends one signed IDR per merge to `main` (`scripts/probat_extend.py`, catch-up semantics — a raced or missed run is healed by the next one, so no merge is silently skipped), and `probat.yml` verifies the grown chain on every push.

## Why this file exists

Three reasons.

**One** — DONNA's value proposition is *delegation proof*. The repository should embody the value proposition, not just describe it. Talking about an audit chain in a README and not having one is the legal equivalent of a contract that says *"trust us"*. The chain has to be live, verifiable, and tied to the work. So we tied it to the only work the repository actually performs: its own commits.

**Two** — *Munir v Secretary of State for the Home Department* [2026] UKUT 81 is now binding authority in the UK that public AI services destroy legal privilege. The Tribunal's distinction between public AI and *"closed-source AI tools which do not place information in the public domain"* turns the audit chain from a feature pitch into a practising-certificate question. PROBAT.md is the smallest possible answer: a working, verifiable audit chain you can read in 30 seconds and reproduce locally in 60.

**Three** — *DONNA probat.* The verb is the brand. If the repository cannot demonstrate the verb, the verb is empty. This file is the demonstration.

## Appendix A · The protocol

Every IDR has six load-bearing fields:

| Field | Purpose |
|-------|---------|
| `decision_id` | Unique identifier (we use timestamp-nanoseconds for stdlib portability; ULID is recommended for production) |
| `timestamp` | ISO 8601 UTC — when the decision was produced |
| `intent` | The structured intent (NOT a transcript — extracted from speech via DONNA's voice surface) |
| `signer` | Who produced this decision: agent ID, human, or hybrid |
| `confidence` | The producer's stated confidence in [0.0, 1.0] |
| `previous_hash` | SHA-256 of the previous IDR's canonical form (or `0…` for genesis) |
| `signature` | HMAC-SHA256 of this IDR's canonical form, signed by the firm-specific key |

`metadata` is a free-form JSON object for context — model name, route, commit SHA, escalation depth, anything the firm wants to track.

The protocol lives openly at [`happi.md` v1.1](https://gist.github.com/architext1/808548dd25cfac5cc47fb6e910b79292). Any AI runtime can read this and produce IDR-compatible records.

## Appendix B · The signing key (and why this is OK to publish)

The signing key for *this repository's* PROBAT.md is the literal string:

```
donna-public-demo-key-2026-05-08
```

This is published deliberately. The chain you are reading is the **demonstration chain** — a public artefact that proves the protocol works end-to-end. Anyone can verify it, anyone can reproduce it, anyone can fork and replace the key with their own.

For a firm-scale deployment, the signing key is firm-specific, never published, rotated on a schedule, and held in the firm's HSM or Keychain — exactly as the firm holds any other privileged secret. The IDR engine that signs production chains is part of the **NEXUS tier**; this README explains the open-source / proprietary boundary.

## Appendix C · A working `bin/notarise demo`

If you have a Python 3.10+ interpreter on `$PATH`, you can reproduce the chain locally in under 60 seconds:

```bash
git clone https://github.com/chiefofstaff-legal/donna.git
cd donna
export DONNA_NOTARISE_KEY=donna-public-demo-key-2026-05-08
bin/notarise demo
```

The output is three IDRs — chained, signed, verifiable — equivalent to the entries above. Pipe it through `bin/notarise verify --chain /dev/stdin` and you get `OK: 3 record(s) verified (HMAC-SHA256)` to stderr.

That is the entire substrate. ~200 lines of stdlib Python. No dependencies. No hidden state. The brand is the verb; the verb is verifiable.
